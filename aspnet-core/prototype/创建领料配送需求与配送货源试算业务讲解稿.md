# 创建领料配送需求与配送货源试算业务讲解稿

本文用于向业务人员介绍原型中的两个重点页面：

- 创建领料配送需求
- 配送货源试算

讲解目标不是介绍页面长什么样，而是让业务人员理解：系统为什么这样设计、每个状态代表什么、操作人员应该按什么顺序处理，以及哪些业务规则需要大家现场确认。

## 一、开场说明

各位老师，今天主要介绍领料配送业务里的两个核心环节。

第一个环节是“创建领料配送需求”。它解决的是：SAP 或前序系统产生领料申请后，哪些领料单需要配送，配送需求要怎么按日期、时段、地点和数量拆出来。

第二个环节是“配送货源试算”。它解决的是：配送需求已经明确后，系统从厂内资材库、供应商送货、码头仓库等货源中试算可用货源，给出建议分配结果，再由业务人员确认。

这两个页面串起来，就是从“领料申请”到“配送需求”，再到“货源确认”的完整前半段流程。后续确认后的结果，会继续支撑生成配送单、仓储任务、派工和执行。

## 二、整体业务流程

可以先用一句话概括：

领料申请单进入系统后，先判断是否需要配送；需要配送的，由业务人员拆解成一个或多个配送需求；配送需求确认后，再进行货源试算和人工确认。

完整流程如下：

1. 查询领料申请单。
2. 查看领料申请单下的物料行项目。
3. 对需要配送的领料单执行“拆解配送需求”。
4. 在拆解弹窗中查看历史拆解记录，填写本次拆解数量、地点、日期和时段。
5. 保存草稿或确认拆解。
6. 已确认拆解的配送需求进入“配送货源试算”页面。
7. 勾选需要试算的配送需求。
8. 执行试算，查看可参与试算的货源。
9. 根据系统建议和人工判断，调整货源确认数量。
10. 确认货源，进入后续配送单和仓储任务环节。

## 三、页面一：创建领料配送需求

### 1. 页面定位

这个页面的定位是“领料申请单到配送需求的入口”。

业务人员在这里主要完成三件事：

1. 找到需要处理的领料申请单。
2. 查看领料申请单下有哪些物料行项目。
3. 对需要配送的领料单进行拆解，生成配送需求。

这个页面不是货源分配页面，也不是仓储任务执行页面。它的重点是“需求拆解”。

### 2. 查询区说明

页面上方是“领料配送需求查询”。

当前查询条件包括：

| 查询条件 | 说明 |
| --- | --- |
| 领料工厂 | 发起领料需求的工厂，例如 2000 |
| 发料工厂 | 实际发出物料的工厂，例如 2601 |
| 领料申请单号 | 用于精确定位某一张领料申请单 |
| 领料申请日期 | 按申请日期筛选 |
| 是否配送 | 区分需要配送和不需要配送的领料单 |
| 配送方式 | 单次配送、多次配送、自行领料 |
| 申请人员工号 | 按申请人筛选 |
| 特殊库存 | 如 B 客户库存、E 现有库存、Q 项目库存 |
| 物料 | 按物料号查询 |
| 描述 | 按物料描述辅助查询 |
| 拆解状态 | 未拆解、部分拆解、已全部拆解、不处理 |
| 货源确认状态 | 未确认、部分已确认、全部已确认、不处理 |

讲解重点：

查询区的设计是为了支持两种场景。

第一种是单据处理场景，业务人员知道领料申请单号，直接输入单号查询。

第二种是批量跟进场景，业务人员按拆解状态或货源确认状态筛选待处理数据。例如筛选“部分拆解”或“未确认”，查看还有哪些单据没有走完。

### 3. 领料配送需求列表

查询结果以领料申请单为主行展示。

主行显示的是单据级信息：

- 领料工厂
- 发料工厂
- 领料申请单号
- 领料申请日期
- 是否配送
- 配送方式
- 申请人员工号
- 申请人电话
- 特殊库存
- 拆解状态
- 货源确认状态
- 操作

这里采用“主表 + 展开明细”的设计。

业务意义是：业务人员先从领料申请单维度判断这张单是否需要处理，再展开查看行项目。这样比直接把所有行项目铺出来更清晰，也更符合实际操作习惯。

### 4. 展开行项目

点击主行左侧的展开按钮后，可以看到该领料申请单下的行项目。

行项目展示字段包括：

- 行项目
- 物料
- 描述
- 申请数量
- 基本单位
- 批次
- 认证种类
- 备注
- 收货库存地点
- 配送日期
- 配送时段
- 最后配送日期

讲解重点：

展开区是为了让业务人员确认“这张领料申请单下面具体有哪些物料、数量和收货地点”。拆解配送需求时，实际拆的是这些行项目的数量和配送计划。

### 5. 拆解状态说明

列表中的拆解状态建议这样向业务解释：

| 状态 | 含义 |
| --- | --- |
| 未拆解 | 领料申请单还没有生成任何配送需求 |
| 部分拆解 | 领料申请单已有部分数量生成配送需求，但还有剩余待拆 |
| 已全部拆解 | 领料申请数量已经全部拆解成配送需求 |
| 不处理 | 该单不进入配送需求拆解流程，例如自行领料或无需配送 |

注意：“拆解状态”只表达需求是否拆出来，不代表货源是否已经确认。

### 6. 货源确认状态说明

货源确认状态建议这样解释：

| 状态 | 含义 |
| --- | --- |
| 未确认 | 已有配送需求，但还没有确认货源 |
| 部分已确认 | 部分配送需求或部分行项目已经确认货源 |
| 全部已确认 | 该领料申请相关配送需求的货源都已确认 |
| 不处理 | 不进入货源确认流程 |

注意：“货源确认状态”是后续试算页面的处理结果，不应该和拆解状态混淆。

### 7. 操作：拆解配送需求

当某张领料申请单需要生成配送需求时，点击“拆解配送需求”。

系统会打开“拆解配送需求”弹窗。

这个弹窗是创建配送需求的核心操作区域。

## 四、拆解配送需求弹窗

### 1. 领料单信息

弹窗顶部显示领料单基本信息：

- 领料申请单号
- 领料工厂
- 申请人员工号

这部分用于让用户确认当前正在处理的是哪张领料申请单，避免误操作。

### 2. 已有拆解记录明细

第二块是“已有拆解记录明细”。

这里展示这张领料申请单之前已经拆出来的配送需求记录。

主要字段包括：

- 配送需求单号
- 行项目
- 物料
- 描述
- 本次数量
- 收货库存地点
- 配送日期
- 配送时段
- 最后配送日期
- 状态
- 操作

这里的作用是让业务人员先看历史拆解，再决定本次怎么拆。

例如当前样例中：

- DELREQ-20260507-001 是草稿状态。
- DELREQ-20260507-002 是已确认状态。
- DELREQ-20260507-003 是已取消状态。

### 3. 历史拆解状态说明

| 状态 | 含义 | 可操作建议 |
| --- | --- | --- |
| 草稿 | 已暂存，但还未正式确认 | 可修改、确认、撤销 |
| 已确认 | 已正式生成配送需求 | 通常不允许直接修改，需走反向或调整流程 |
| 已取消 | 该拆解记录已取消 | 只作为历史记录保留 |

讲解时建议强调：

草稿数量和已确认数量在业务含义上不一样。已确认数量已经进入后续流程；草稿数量只是计划或临时保存，是否占用待拆数量需要业务确认口径。

### 4. 本次拆解填写

第三块是“本次拆解填写”。

这里是用户本次实际录入配送需求的地方。

公共字段包括：

- 收货库存地点
- 配送日期
- 配送时段
- 最后配送日期

下面的明细表按行项目录入本次数量：

- 行项目
- 物料
- 描述
- 申请数量
- 待拆数量
- 本次数量
- 配送需求单号

其中“配送需求单号”显示为系统生成，表示用户确认后由系统生成正式配送需求编号。

### 5. 本次数量颜色反馈

当前原型中，本次数量有行级颜色提示：

| 颜色 | 含义 |
| --- | --- |
| 绿色 | 本次数量已填写且大于 0 |
| 红色 | 本次数量为空或等于 0 |

讲解重点：

这个颜色只提示“这行是否填写有效数量”，不代表已经完全拆完，也不代表数量一定合法。

例如，本次数量填 20 会显示绿色；填 0 或不填会显示红色。

后续正式系统还需要增加数量校验：

- 本次数量必须大于 0。
- 本次数量不能大于待拆数量。
- 如果允许部分行不拆，需要明确红色行是否允许保存草稿或确认拆解。

### 6. 保存草稿

点击“保存草稿”，表示本次拆解先暂存。

适用场景：

- 业务人员还没有最终确认配送日期或时段。
- 需要先记录一个计划，后续再确认。
- 多人协同处理时，先保存当前录入内容。

讲解时可以强调：

草稿不应直接进入货源试算，只有确认后的配送需求才进入后续试算。

### 7. 确认拆解

点击“确认拆解”，表示本次填写内容正式生成配送需求。

确认后应产生正式的配送需求单号，并进入“配送货源试算”页面进行货源确认。

正式系统建议在确认时做以下校验：

- 本次数量必须大于 0。
- 本次数量不能超过待拆数量。
- 配送日期、配送时段、最后配送日期不能为空。
- 最后配送日期不能早于配送日期。
- 同一配送需求是否允许包含多个收货库存地点，需要业务确认。

## 五、页面二：配送货源试算

### 1. 页面定位

配送货源试算页面的定位是“给已确认的配送需求寻找和确认货源”。

业务人员在这里主要完成四件事：

1. 查询待确认货源的配送需求。
2. 勾选需要试算的配送需求。
3. 执行试算，查看系统建议货源。
4. 根据业务判断调整确认数量，并确认货源。

### 2. 查询区说明

页面上方是“配送需求查询”。

查询条件包括：

| 查询条件 | 说明 |
| --- | --- |
| 领料工厂 | 查询指定领料工厂下的配送需求 |
| 发料工厂 | 查询指定发料工厂下的配送需求 |
| 领料申请单号 | 根据原始领料申请单查找配送需求 |
| 物料 | 按物料号筛选 |
| 描述 | 按物料描述辅助筛选 |
| 收货库存地点 | 按配送目的地筛选 |
| 货源确认状态 | 未确认或已确认 |

讲解重点：

这个页面查的是“配送需求”，不是原始领料申请单。领料申请单号只是溯源字段，用于帮助用户快速定位。

### 3. 配送需求列表

列表以配送需求单为主行展示。

主要字段包括：

- 领料工厂
- 发料工厂
- 领料申请单号
- 领料申请日期
- 配送需求单号
- 收货库存地点
- 配送日期
- 配送时段
- 最后配送日期
- 货源确认状态
- 操作

主行左侧可以展开查看配送需求下的行项目。

### 4. 勾选与批量试算

列表左侧有复选框，可以勾选需要试算的配送需求。

需要注意：只有“未确认”的配送需求才展示复选框并参与试算；已经确认货源的配送需求不展示复选框，不参与批量试算。

顶部按钮会显示当前选中数量，例如：

- 执行试算+1
- 执行试算+2

这个设计的作用是降低误操作风险，让用户清楚知道本次会对几条配送需求执行试算。

表头复选框支持全选和半选状态：

- 没有选中时，不勾选。
- 选中部分行时，显示半选状态。
- 全部选中时，显示选中状态。

建议讲解时提醒业务：

已确认货源的配送需求不再进入试算选择范围，页面只保留“查看货源结果”，用于追溯已经确认的货源明细。

### 5. 行内操作

未确认的配送需求可以点击“执行试算”。

已确认的配送需求可以点击“查看货源结果”。

这两个动作的区别是：

- 执行试算：进入试算和人工确认流程。
- 查看货源结果：只查看已经确认过的货源，不再重新计算。

### 6. 展开配送需求行项目

点击配送需求行左侧展开按钮，可以查看该配送需求包含哪些物料行。

行项目字段包括：

- 行项目
- 物料
- 描述
- 数量
- 基本单位
- 批次
- 认证种类
- 备注

这里用于确认“本张配送需求到底需要配送什么物料、多少数量”。

## 六、货源分配试算弹窗

点击执行试算后，打开“货源分配试算”弹窗。

这个弹窗分成三块：

1. 配送需求明细行
2. 可参与试算货源
3. 货源分配结果

### 1. 配送需求明细行

第一块展示当前参与试算的配送需求明细。

字段包括：

- 配送需求单号
- 领料工厂
- 发料工厂
- 领料申请单号
- 行项目
- 物料
- 描述
- 数量
- 基本单位
- 批次
- 认证种类
- 收货库存地点
- 配送日期
- 配送时段
- 最后配送日期

讲解重点：

这里是试算输入条件。系统会根据这些需求行去匹配可用货源。

### 2. 可参与试算货源

第二块展示系统找到的候选货源。

货源类型包括：

- 厂内资材库
- 供应商送货
- 码头仓库

候选货源字段包括：

- 物料
- 描述
- 批次
- 认证种类
- 货源类型
- 货源标识
- 可供量
- 基本单位
- 仓库号
- 仓储类型
- 仓位
- 发料工厂
- 库存地点
- 库存类型
- 预约送货单号
- 收货日期
- 内向交货单
- 码头免堆日期
- 逾期延滞费
- 转栈日期
- 特殊库存标识
- 特殊库存编号
- 是否免检
- 检验日期
- 延滞成本
- 逾期滞留费
- 作业成本

讲解重点：

这张表解释“系统为什么能分配这些货源”。它不是最终结果，而是候选池。

其中：

- 厂内资材库通常看库存地点、仓储类型、仓位、库存类型、检验状态。
- 供应商送货通常看预约送货单号、是否免检、预计到货或可用情况。
- 码头仓库通常看码头免堆日期、延滞成本、逾期滞留费、转栈日期。

### 3. 货源分配结果

第三块是系统建议和人工确认的最终工作区。

字段包括：

- 配送需求单号
- 发料工厂
- 领料申请单号
- 行项目
- 物料
- 描述
- 货源类型
- 货源标识
- 系统建议
- 人工确认数量
- 基本单位
- 延滞成本
- 逾期滞留费
- 作业成本
- 分配总成本
- 校验结果
- 不选/调整原因

### 4. 系统建议与人工确认

“系统建议”表示系统根据当前规则给出的建议分配数量。

“人工确认数量”允许业务人员调整。

这样设计是因为系统可以提供建议，但现场业务可能有额外判断。例如：

- 某个货源虽然成本低，但现场暂时不方便作业。
- 某个码头货源虽然有成本，但需要优先处理免堆风险。
- 某个供应商送货虽然可用，但预计到货不稳定。
- 业务人员决定先不选某个货源，需要填写调整原因。

### 5. 货源分配结果颜色反馈

当前原型中，货源分配结果支持行级颜色反馈：

| 颜色 | 含义 |
| --- | --- |
| 绿色 | 人工确认数量满足该需求行数量 |
| 红色 | 人工确认数量未满足该需求行数量 |

例如：

- 需求 20，人工确认 20，显示绿色。
- 需求 20，人工确认 0，显示红色。

讲解重点：

这个颜色帮助用户快速发现哪些行还没满足。正式系统还应同步更新“校验结果”字段，例如红色时显示未满足，绿色时显示满足。

### 6. 不选/调整原因

当人工确认数量和系统建议不一致时，建议填写“不选/调整原因”。

例如当前样例：

系统建议码头仓库分配 20，但人工确认数量改成 0，原因填写“人工改为0，改用厂内库存补足”。

这里需要业务确认一个关键规则：

如果写了“改用厂内库存补足”，系统结果里是否必须展示被替代的厂内货源行？

建议正式系统必须展示替代货源，否则结果闭环不完整。

### 7. 重新试算

点击“重新试算”，表示重新调用试算逻辑。

适用场景：

- 用户调整了人工确认数量后，希望重新生成建议。
- 有新的库存或预约数据同步进来。
- 用户希望恢复系统建议。

建议业务确认：

重新试算时是否保留人工调整？

可选口径：

1. 完全覆盖人工调整。
2. 保留人工调整，仅重算未确认部分。
3. 弹窗提示用户选择是否保留。

### 8. 确认货源

点击“确认货源”表示本次分配结果正式生效。

正式系统建议在确认前做强校验：

- 人工确认数量必须大于等于 0。
- 人工确认数量不能超过需求数量。
- 人工确认数量不能超过货源可供量。
- 未满足的行不能直接全部确认。
- 如果允许部分确认，状态应变为“部分已确认”。
- 人工确认数量为 0 且与系统建议不一致时，必须填写调整原因。
- 替代货源必须在结果表中体现。

## 七、查看货源结果

对于已经确认货源的配送需求，用户可以点击“查看货源结果”。

该弹窗展示已确认的货源明细，包括：

- 配送需求单号
- 领料申请单号
- 行项目
- 物料
- 描述
- 批次
- 认证种类
- 货源类型
- 货源标识
- 确认数量
- 仓库号
- 仓储类型
- 仓位
- 发料工厂
- 库存地点

讲解重点：

这个页面不是重新试算，而是结果追溯。它帮助用户回答：这笔配送需求最终用了哪个货源、确认了多少数量、来源位置在哪里。

## 八、建议现场演示顺序

建议明天演示时按以下顺序走：

1. 打开“创建领料配送需求”。
2. 介绍查询条件，说明可以按单号、状态、物料筛选。
3. 展示领料配送需求列表，说明主表是领料申请单维度。
4. 展开 1000000137，说明行项目明细。
5. 点击“拆解配送需求”。
6. 介绍领料单信息。
7. 介绍已有拆解记录明细，重点说明草稿、已确认、已取消。
8. 介绍本次拆解填写，说明收货地点、配送日期、时段、最后配送日期。
9. 演示本次数量为空或 0 时变红，大于 0 时变绿。
10. 说明保存草稿和确认拆解的区别。
11. 切换到“配送货源试算”。
12. 介绍配送需求查询条件。
13. 介绍配送需求列表，说明主表是配送需求单维度。
14. 勾选配送需求，展示“执行试算+1”的含义。
15. 展开配送需求，说明配送需求行项目。
16. 点击执行试算。
17. 介绍配送需求明细行。
18. 介绍可参与试算货源，说明厂内、供应商、码头三类货源。
19. 介绍货源分配结果，说明系统建议和人工确认数量。
20. 演示人工确认数量为 0 时红色，满足数量时绿色。
21. 说明不选/调整原因。
22. 说明重新试算和确认货源。
23. 打开查看货源结果，说明确认结果可追溯。

## 九、需要业务人员重点确认的问题

建议明天最后集中确认以下问题。

### 1. 草稿是否占用待拆数量

当前页面中待拆数量更接近“申请数量 - 已确认数量”。

需要确认：草稿是否要占用待拆数量？

如果草稿占用，待拆数量要扣除草稿。

如果草稿不占用，草稿只作为临时计划展示。

### 2. 本次拆解是否允许部分行为空

当前颜色规则是：

- 本次数量大于 0，绿色。
- 本次数量为空或等于 0，红色。

需要确认：确认拆解时是否允许存在红色行？

如果允许，表示本次只拆部分行。

如果不允许，确认拆解时必须拦截。

### 3. 本次数量是否必须小于等于待拆数量

建议必须限制。

否则用户可能录入超过待拆数量的值。

### 4. 一个配送需求是否允许多个收货库存地点

如果允许，配送需求单下可以有多个收货地点。

如果不允许，系统应按收货库存地点拆成不同配送需求单。

### 5. 已确认货源的配送需求是否允许再次试算

建议默认不允许。

已确认的配送需求只允许查看货源结果。若需要重新试算，应走反确认或调整流程。

### 6. 重新试算是否保留人工调整

需要确认重新试算时：

- 是否覆盖人工确认数量。
- 是否保留人工修改。
- 是否只重算未满足部分。

### 7. 人工改为 0 时是否必须填写原因

建议必须填写。

特别是系统建议有数量，但人工确认改为 0 时，必须说明原因。

### 8. 替代货源是否必须展示在结果表

建议必须展示。

如果原因写“改用厂内库存补足”，结果表里就应该出现补足的厂内货源行，否则结果不闭环。

### 9. 校验结果是否要跟颜色同步

建议同步。

当人工确认数量满足需求时，校验结果显示“满足”。

当人工确认数量不满足需求时，校验结果显示“未满足”或“未选”。

### 10. 货源选择规则优先级

需要业务确认系统建议的优先级：

- 优先成本最低？
- 优先可用时间最早？
- 优先厂内库存？
- 优先处理码头免堆风险？
- 优先免检货源？
- 是否考虑作业能力和装载限制？

这些规则会直接影响系统建议结果。

## 十、收尾说明

最后可以这样总结：

这两个页面的设计目标，是把领料配送从人工判断推进到系统化管理。

“创建领料配送需求”解决的是需求怎么拆、什么时候送、送到哪里、送多少。

“配送货源试算”解决的是从哪里送、系统建议用什么货源、人工最终确认多少。

当前原型已经把主流程、主要状态和关键操作串起来了。明天讨论的重点不是页面字段够不够多，而是确认业务口径：哪些状态可以流转、哪些数量必须校验、哪些异常必须拦截，以及系统建议货源的规则优先级。
